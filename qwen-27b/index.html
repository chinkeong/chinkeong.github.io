How to run Qwen3.8-27B well on whatever you have — RTX 30/40/50 series, DGX Spark (GB10), Intel Arc Pro B50/B70, or an Intel Arc B390-class iGPU. Grounded in measured runs on an RTX 3090 and fact-checked against published specs and community benchmarks.

01

The model, in five facts that drive every setting

  • Hybrid attention. Most of its 64 layers use Gated DeltaNet, a linear-attention design whose memory use stays constant no matter how long the context gets; only 16 of the 64 are standard attention layers (and those use GQA with 4 KV heads). The result: KV costs just 64 KiB per token at fp16 — 4.0 GiB at 122k context with a Q8 cache, 7.5 GiB unquantized — where a dense 27B storing KV in every layer would need exactly 4× as much. Huge contexts are cheap in memory, and speed falls off gently as they fill rather than collapsing.
  • Native 262,144 context. No YaRN or rope tricks needed below that; the limit you'll actually hit is VRAM, not the model. (The model card lists extension to 1M via YaRN — out of scope here: the KV cache alone would run ~34 GiB even at q8_0.)
  • Thinking always on, defaulting to xhigh. Reasoning tokens share the context window with your prompt and output — a 100k-token thinking run needs a >100k window (§04).
  • Vision is optional at serve time. The BF16 mmproj projector costs ~0.9 GB of VRAM; drop it for text-only work.
  • Official thinking-mode sampling: temp 1.0 · top-p 0.95 · top-k 20 · min-p 0. Clients that silently send temperature 0 (aider does) cause repetition loops — override them.

02

The physics: bandwidth is king, and VRAM is a cliff

Generation speed comes down to one ratio: how fast your card can read memory, divided by how much it must read per token. Every token requires reading the entire model — about 16.5 GB for a 4-bit quant. So take your card's bandwidth in GB/s, divide by 16.5, multiply by ~0.7 (the efficiency we measured on CUDA), and that's your speed ceiling in tokens per second. This one calculation predicts every row of the matrix in §07.

The second law: speed vs. context is a cliff, not a curve. Flat while weights + KV fit in VRAM; a collapse once anything spills over the PCIe bus — and the magnitude scales with how much spills: ~10× when the weights file itself lands in system memory (the 256k point below), a measured 1.5–2× from even a ~2 GB spill (§10). Corollary

Allocated is not the same as used: a big context window with a small prompt in it costs VRAM, not speed. And as long as you stay below the cliff, shrinking the window gains you nothing — there is no hidden "optimal point" to search for.

That corollary now has a measured face. Probed 2026-08-22 with Q4_K_M (q8_0 KV, MTP on, mmproj loaded — the ~1 GiB-larger UD-Q4_K_XL shifts every ceiling below ~30k tokens lower, while dropping --mmproj frees ~0.9 GiB and raises them ~27k, to roughly ~158k fully resident) by stepping -c upward with short temp-0 decode probes: speed holds at 50–55 t/s all the way to -c 212992, turns borderline at 217,088 (41.2 t/s), and collapses at 221,184 (19.5 t/s). But nvidia-smi tells the other half of the story: dedicated VRAM hits its ~24 GB ceiling already at -c 131072 (measured 24,052 MiB) — past that point the KV cache is overcommitted, and the run stays fast only while a short prompt leaves the deep pages untouched. So a 24 GB card has two ceilings, not one: ~131k is the practical fully-resident ceiling — fast even when a long run actually fills it, though it sits right at the margin (the recipe's 122,880 deliberately leaves headroom below it), and it is the same number the budget table's arithmetic lands on below — while up to ~213k loads and runs fine for shallow use, degrading progressively as real tokens land in the overcommitted tail.

Two footnotes the table earns. First, the q4_0-KV flag: the problem is not that quantization error "accumulates" — each cache entry is quantized once — it's that at long context every new token attends over hundreds of thousands of perturbed entries, and retrieval gets flaky at exactly the 200k+ lengths a q4_0 cache would enable. q8_0 is the deepest safe cut. Second, prefill: these budgets make a 200k+ prompt fit, but filling it is quadratic work on the 16 full-attention layers — a genuinely full 100k prompt takes several minutes to first token on a 3090, potentially tens of minutes at full 200k+ (an estimate, not a benchmark; the reference run's ~2k prompt hides this cost entirely).

03

Universal rules — true on every card

  • One token pool. prompt + thinking + output ≤ context. The model has no awareness of its limits and cannot budget its own thinking; limits are enforced by your config only.
  • Cut-offs are client-side. The server generates until told to stop. Truncations come from the client's max_tokens, its request timeout, or Ctrl+C — and with OpenAI-compatible APIs a cut generation cannot seamlessly resume. Size max_tokens and the client timeout so the whole run fits one response.
  • One slot, quantized KV. --parallel 1 (some UIs default to 2 = double KV) and -ctk q8_0 -ctv q8_0 (halves KV, negligible loss — but never q4_0 for the KV cache; why: §02).
  • --load-mode none on RAM-tight machines (replaces the deprecated --no-mmap). Otherwise the whole GGUF stays cached in system RAM even after the weights are in VRAM — ~15 GB freed for the Q4 file, at the cost of a slower model load.
  • All layers on GPU or accept the cliff. Partial offload speed is set by CPU RAM bandwidth, not by the GPU — a 5080 and a 4060 Ti offload at nearly the same ~8–12 t/s. And this is a dense model: the MoE escape hatch of parking expert tensors on CPU (-ot) has nothing to target here, so every offloaded layer sits on the critical path of every token. (Two ways this rule silently breaks: §10.)

Rule of thumb

For a benchmark, use the same quant on every machine (Q4-class) — a different quant is a different model and its scores aren't comparable. For daily use, pick the best quant that fits entirely in your VRAM.

Does FP4 beat INT4? A scored smoke test

First, what the two formats actually are. A 4-bit quant stores each weight as one of only 16 allowed values — the formats differ in where those 16 values sit:

A common belief says floating-point formats always beat integer formats at the same bit width. We tested it: the three quants above, graded for correctness on GSM8K and MATH-500 (20 problems each, greedy decoding, identical prompts, 4096-token budget; answers that ran out of budget mid-thinking count as wrong and are reported as truncations). One framing rule before the numbers: at 20 problems this is a smoke test, not a ranking. (Throughout this guide a point means a percentage point of accuracy — 94% → 95% is one point. It is an absolute unit, unlike "percent better", which is relative; and in a scored run, points and questions are chained together: at n=20 each question is worth 5 points, at n=200 each is worth 0.5.) The smoke test's job is to catch a broken quant — a bad conversion or mangled chat template collapses a score by 20–40+ points, which even n=20 detects reliably. It cannot rank healthy quants, whose true gaps are a point or three (the arithmetic is in §09). What the numbers say:

  • "Floating point always wins" did not survive the test. All three tied on GSM8K; on MATH-500 the integer-grid K-quant answered two more problems than either FP4 file. At 20 samples that edge is weak evidence — but it is the opposite direction from the belief. What actually decides 4-bit quality is how cleverly a format spends its bits — block sizes, scale precision, which layers stay high-precision — and mature K-quants are very good at that game. Both families use fine-grained scaling; the float-vs-integer grid underneath matters far less than people assume.
  • The two NVFP4 tiers were indistinguishable at this sample size — which is expected under noise, not evidence of equivalence. The file structure does predict a tie, though: the family shares one byte-identical NVFP4 backbone, with tiers differing only in the surrounding layers. The surprise is where VERY-LOW's savings actually landed: on these math prompts at n-max 10 its MTP draft head drafted noticeably worse (acceptance length 3.33 vs ~4.8) — a speculative-decoding speed cost, not an accuracy one. The penalty is config-dependent, though (n-max and p-min are the speculation knobs §06 tunes): re-measured 2026-08-22 at the tuned n-max 4 / p-min 0.75 on code generation, both tiers accepted identically (0.83) and VERY-LOW was the faster file (54.6 vs 48.2 t/s) — smaller weights, less memory traffic per token.
  • Sample-size honesty: each problem is worth 5 points. Every gap in this table is one or two questions wide. Treat it as "no meaningful quality difference, mild edge to the K-quant" — not a ranking. We also ran the same prompts through a different serving stack and grader version and saw individual cells move by up to 10 points, which means measurement variance is the same size as the differences being measured. Anyone showing you a one-run quant ranking without error bars is selling something. §09 puts numbers on exactly how underpowered a 20-question run is.
The takeaway

Pick your file by size and speed, not by format ideology: on a 24 GB Ampere card that means Q4_K_M (fastest, best-drafting MTP head — the n=20 smoke test found nothing against it, and the measured wikitext perplexity below comes out in its favor). NVFP4's real advantages live on Blackwell hardware where the format runs natively.

Accuracy at 20 questions cannot separate healthy quant files (§09 carries the full arithmetic) — but per-token metrics can. Perplexity here is the classic model-quality metric, not the search engine (which named itself after it): run the model over real text and score how well it predicted each actual next token. A perplexity of 6.5 means that at every step the model was, on average, as uncertain as choosing between ~6.5 equally likely words — perfect prediction would be 1, and lower is better. Because quantization damage makes prediction slightly worse everywhere, this metric feels it at all ~330k token positions instead of collecting one right/wrong bit per benchmark question. 06

Speculative decoding — free speed, priced in acceptance

Speculation is lossless: every drafted token is verified by the full model before it counts, so quality is never on the table — only speed is, and the speedup is set by draft acceptance, which your content decides. The subsections below measure it, tune it, and show how a clean benchmark overstated it. MTP speculative decoding — free speed on every GPU

Qwen3.8-27B ships with a built-in multi-token prediction (MTP) draft head — a small helper network that guesses several tokens ahead so the full model only has to check them, which is much faster than generating each one. The standard K-quant GGUFs (§05's table) already include it (the head itself always stays at 8-bit, whatever the main quant). llama.cpp added support in July 2026, and because every guess is verified by the full model before it's accepted, the output is exactly what the model would have written anyway — you only gain speed. It works on any GPU llama.cpp supports: Ampere, Ada, Blackwell, Arc, iGPUs.

  --spec-type draft-mtp  --spec-draft-n-max 4  --spec-draft-p-min 0.75

How much speed it adds depends heavily on hardware and workload — reports range from +33% to +145%. An RTX 5090 tester saw 148 avg / 203 peak t/s on the NVFP4 tiers. On our reference 3090, generation went from 40.3 to 58–60 t/s — +45% at the default-ish settings (n-max 4, 89% of drafted tokens accepted) — and on the original benchmark prompt, tuning pushed it to 81.7 t/s, +105% (n-max 10, p-min 0.5) — though a 2026-08-22 re-sweep on realistic code inverted that ranking in favor of n-max 4 / p-min 0.75 (57.9 vs 48.3 t/s; the full story, and the mechanism behind the flip, is in the sweep section below). The warning all these numbers carry: benchmark on your own machine. That 5090 tester found n-max 4 fastest with 6–8 slower; our 3090 agreed on real code yet kept climbing to n-max 10 on its near-ideal prompt — the optimum moves with hardware and content, so there is no universal best value. You'll need a llama.cpp build recent enough to have the draft-mtp feature.

One more measured nuance before you pencil 82 t/s into your plans: the speedup is set by draft acceptance, and acceptance is set by your content. The head only wins when its guesses match what the full model was about to write — easy for boilerplate and predictable code, hard for prose that could go anywhere. What to actually expect

The 81.7 t/s headline is real, but it is a best case — near-ideal acceptance on highly predictable output. On everyday prose and code the same flags measured 44–52 t/s: still free speed, just not double (and the re-swept n-max 4 / p-min 0.75 does better on exactly this content — 57.9 t/s on the code probe). And the model card's official temp 1.0 sampling randomizes exactly the tokens the drafter must guess, so long thinking-heavy runs land lower still. Speculation never costs output quality; on unlucky content it just stops paying.

Acceptance is the speed

The cleanest demonstration we measured (2026-08-22): same card, same flags (n-max 10, p-min 0.5, temp 0), only the content differs. Generating novel code: 53 t/s — acceptance 0.47, mean accepted run 4.0 of 10 drafted. Copying a provided snippet verbatim: 119.8 t/s — acceptance 0.93, mean run 9.9 of 10. A 2.3× speed difference with identical settings. Draft acceptance is not a detail of speculative decoding, it is the whole mechanism — which is why a speculative benchmark number quoted without its acceptance rate is unfalsifiable.

DFlash2 — block drafting (PR stage)

DFlash2 drafts differently from MTP: instead of guessing one token at a time, it predicts a whole 7-token block in a single pass, then picks the most plausible sequence out of the candidates it considered for each position. Like MTP, every draft is verified before it's accepted, so the output is identical to running the model alone. The costs: a separate 1.14 GB drafter model to download (incoai/Qwen3.8-27B-DFlash2-GGUF, ~1.2 GB of VRAM), and — until llama.cpp PR 27342 is merged — building llama.cpp yourself from that branch.

Reading acceptance tables

Published speculative-decoding tables (like the DFlash2 blog's "mean acceptance length") are speed numbers, not quality scores. The verify step guarantees every configuration writes exactly what the base model would have written — a higher acceptance number just means more tokens got through per check. Quality only changes when the weights change (a different quant); speed only changes when the drafter changes.

How big must a benchmark sample size be?

A worked example from this guide's own data. A GSM8K score of 85% at 20 questions carries a 95% confidence interval of roughly 64–95% (Wilson) — a thirty-point window around a table where every score sits within ten points of every other. One flipped question moves a score 5 points. Healthy Q4-class quants differ by perhaps 1–3 true points; inside that window, such a gap is invisible. The principle generalizes to any benchmark of any size: the question is never "is n big enough?" in the abstract, but "is n big enough for the gap I need to see?"

The arithmetic is unforgiving because sampling noise shrinks with the square root of the sample count: halve the gap you want to detect and you need four times the samples. What that costs on this 3090 — paired evaluation on the same questions, temp 0, ~80% base accuracy, 95% confidence at 80% power, ~1,200 tokens per sample at ~55 t/s:

True gap to detectSamples neededWall clock per model
~20 pts — a broken quant~25–30~9–11 min
~10 pts~100–150~35–55 min
~5 pts~300–500~2–3 h
1–3 pts — typical Q4 vs Q4~2,000–10,000~12–60 h

The first row is the one job a local accuracy run does well — and the only claim §05's scored smoke test makes. The last row is why nobody ranks healthy quants by accuracy scores: the run that could would take days per model.

The right tool

KL-divergence and perplexity rank quants; a small-n accuracy pass smoke-tests everything those metrics can't see. Logit-level metrics compare per-token probabilities against the full-precision model over ~330k token positions in an estimated ~15–30 min per model on a 3090-class card (an estimate, not a benchmark from this guide — that covers the per-quant pass against saved full-precision baseline logits; generating the baseline itself needs the BF16 model, which exceeds a 3090's VRAM, and is a slower one-time cost), resolving differences no feasible accuracy run can — which is why quant authors themselves (unsloth's Dynamic 3.0, for example) compare files this way. But they run below the sampling and template layer, so a broken chat template or mangled tool-call format sails through them unnoticed while collapsing scored answers by 20+ points. Run both: KLD to pick between files, one cheap accuracy pass to confirm the file you picked actually works end to end — §05's perplexity table is this advice in practice.

When it silently runs at half speed

Two failure modes produce the same complaint — the command that did 40 t/s yesterday does 25 today — while the server starts cleanly and reports nothing wrong. Both were measured on the reference 3090 (2026-08-22), and both are configuration, not hardware.

Failure 1 · The silent VRAM spill

The NVIDIA driver does not refuse an allocation that exceeds VRAM — by default it quietly overflows into shared system memory across the PCIe bus. On the reference machine, two open browsers held ~2–3 GB of VRAM; the 122,880-context config needed ~22 GiB (§02's budget table); about 1.9 GB spilled. The server loaded without a single warning and decoded at 20–35 t/s — and stayed there no matter how far the context was shrunk, because the weights stay spilled either way. This is §02's cliff in its most treacherous form: the cliff is invisible to the server. Nothing errors, nothing is logged, everything just runs at half its speed or worse.

The signature lives in Task Manager: dedicated GPU memory pinned at 23.5–24.0 / 24.0, shared GPU memory growing, CPU around 70% from driver paging. The fix is freeing the VRAM (close the apps holding it). The prevention is making the failure loud: NVIDIA Control Panel → Manage 3D Settings → Program Settings → llama-server.exe → CUDA — Sysmem Fallback Policy → Prefer No Sysmem Fallback. With that set, an over-budget load fails with an out-of-memory error at startup instead of running slow all day.

Failure 2 · The -ngl off-by-one

llama.cpp counts the output projection as one more "layer" than the model has transformer layers. This model has 64, so -ngl 64 reads as complete — and leaves the output layer, a 5120 × ~151k-vocab matmul that runs for every generated token, on the CPU. Measured cost: decode 25.7 vs 39.7 t/s, prefill 106 vs 290 t/s, GPU utilization 53–67% instead of ~90%, and a stack of CPU threads pinned doing the vocab matmul. The recipes in §08 all say -ngl 99 for exactly this reason: any number past the real count means "everything", with no off-by-one to get wrong. One log line to read carefully: failed to fit params to free device memory: n_gpu_layers already set by user only means an explicit -ngl overrode the automatic fit — any value triggers it, -ngl 99 included. When 27B is enough — and when the frontier earns its keep

A closing dose of perspective — with a disclosure up front: unlike everything above, this section is reasoned, not measured. The question it answers is the one every local-inference guide dodges: which tasks should you trust this machine with? A model does not need trillions of parameters to act as an encyclopedia. High-frequency knowledge — geography, mainstream history, standard biology, common coding syntax — compresses comfortably into 27B, which is why local factual Q&A feels frontier-grade. What trillion-class models buy with their scale is different in kind, not degree: they hold up as reasoning engines, software architects, and autonomous agents. The boundary runs through five territories:

  • Long-horizon reasoning. Direct questions are effortless at 27B; what degrades is the 30-step deduction, the formal proof, the architecture analysis — work where one early flaw silently poisons everything downstream. This guide's §04 judging located the local edge precisely: at xhigh, the 27B delivered 100% of a complex single-file spec, twice. Multi-file systems, where the flaws hide in the seams between files, are where the footing gives.
  • The long tail of knowledge. 27B keeps what training data repeated often; trillion-class models also retain the rare — the niche legal precedent, the legacy framework, the unusual drug interaction. The danger is the local failure mode: on obscure ground a small model does not say "I don't know" — it hallucinates fluently. Treat confident answers about rare domains as unverified drafts.
  • Ultra-long recall. A whole codebase or a 500-page audit in one prompt is two problems wearing one coat: holding the text, which this card's 122k window does (§02), and keeping every cross-document dependency straight, which scales with attention capacity — the part parameters pay for.
  • Multi-constraint instruction following. "Five custom API rules, strict typing, an exact JSON schema, and ten edge-case tests — simultaneously." Rule stacks like that degrade small models first, and quietly: the answer looks compliant until the fourth constraint is checked. Fidelity under heavy constraints is one of the clearest scale dividends.
  • Autonomous agentic reliability. An agent that calls tools, reads its own error logs, and self-corrects across dozens of steps multiplies its per-step error rate through every step. Small errors compound into drift; drift compounds into failure. This is why the setups in the next section shine for supervised sessions and wobble on multi-hour autonomous loops — and why §04's defect cliff matters most in exactly this mode, where nobody is watching the output.

      "name": "llama-server (local)",
      "options": { "baseURL": "http://localhost:1234/v1", "apiKey": "dummy" },
      "models": {
        "qwen/qwen3.8-27b": {
          "name": "Qwen3.8 27B (local)",

Two gotchas from the docs: baseURL must sit inside options, not at the provider root, and the provider id must be a custom name ("llamacpp", "local") — reusing a built-in provider name breaks resolution. (llama.cpp example)

aider · the git-native pair-programmer

The most detailed walkthrough of the five — its metadata/limits pattern is the template every other client repeats in its own config format.

Step 1 · Install aider

# needs Python 3.9+ — any one of these:
python -m pip install aider-install && aider-install   # official installer (recommended)
pip install aider-chat                                 # plain pip
uv tool install --force --python python3.12 aider-chat # uv, isolated env

Step 2 · Point aider at the server

Aider's openai/ model prefix means "any OpenAI-compatible server" — llama-server and OpenVINO Model Server both qualify. Set two environment variables (the key is required by aider; make it match the server's --api-key if you set one, otherwise any placeholder works):

# Windows (cmd / batch)                              # Linux / macOS
set OPENAI_API_BASE=http://localhost:1234/v1         export OPENAI_API_BASE=http://localhost:1234/v1
set OPENAI_API_KEY=dummy                             export OPENAI_API_KEY=dummy

Step 3 · Tell aider the model's limits

Aider knows nothing about a local model until you describe it. Create .aider.model.metadata.json in the directory you launch aider from (or your home directory). Match max_input_tokens to the server's -c value — these two numbers drifting apart is the classic silent failure:

{
    "openai/qwen/qwen3.8-27b": {
        "max_input_tokens": 122880,
        "max_tokens": 106496,
        "input_cost_per_token": 0,
        "output_cost_per_token": 0,
        "supports_vision": true
    }
}

The model name after openai/ must match what the server reports at /v1/models — llama-server sets it with --alias, so the recipes above all serve as qwen/qwen3.8-27b.

Step 4 · Fix aider's defaults for a thinking model

Aider sends temperature 0 by default — a repetition-loop trigger on reasoning models — and needs to know to strip <think> blocks before parsing edits. Create .aider.model.settings.yml next to the metadata file:

- name: openai/qwen/qwen3.8-27b
  use_temperature: 1.0
  reasoning_tag: think
  extra_params:
    top_p: 0.95

Step 5 · Launch

aider --model openai/qwen/qwen3.8-27b --edit-format diff --timeout 3600
  • --edit-format diff — the model writes only changed hunks instead of whole files. On local t/s this is the biggest quality-of-life setting there is: a 60 KB file edit drops from minutes to seconds. Diff also degrades gracefully on cut-offs (complete hunks still apply).
  • --timeout 3600 — long thinking runs outlive default client timeouts; the server log shows a timeout as "Client disconnected. Stopping generation".
  • First run sanity checks: the model-warning banner should be gone (metadata file found), and the banner should read diff edit format. If edits arrive mangled, the fallback is removing --edit-format diff to use whole-file mode.
  • Vision: with supports_vision: true and the server launched with --mmproj, you can /add screenshot.png in aider and the local model will see it.

DeepSeek Harness · plugin-based agent framework (developer preview)

# run the web UI:
npx @deepseek-ai/dsh web
# custom OpenAI-compatible providers live in $DSH_HOME/settings.yaml:
llm-pi-ai:
  providers:
    llamacpp:
      api: openai-completions
      baseURL: http://localhost:1234/v1
      apiKeyEnv: LLAMA_API_KEY        # set LLAMA_API_KEY=dummy to match --api-key
      compat:
        supportsDeveloperRole: false  # llama-server wants a plain system role
        maxTokensField: max_tokens
      models:
        - id: qwen/qwen3.8-27b
          input: [text, image]        # vision works when the server runs with --mmproj

The harness's headline trick is routing: it plans with heavy reasoning, then fans the plan out to sub-agents that execute with light reasoning. Two things to know when backing it with llama-server. First, llama-server ignores a per-request reasoning_effort field (same dialect issue as Pi above) — effort is fixed server-side via --chat-template-kwargs, so either run one server at xhigh (this guide's quality-first default), or run two llama-server instances (one xhigh planner on one port, one low executor on another) and register both as separate models in settings.yaml — the harness can then route between them. Second, its parallel sub-agents each hold their own context: with --parallel 1 (this guide's recipes) requests queue rather than run concurrently, which is correct on a single 24 GB card — raising --parallel multiplies KV cache and walks you off the §02 cliff. For non-thinking "fast mode" runs, Qwen's official instruct sampling is temp 0.7 · top-p 0.8 · presence penalty 1.5.

One rule for all agents

Whatever the agent, its context and max-output settings must match the server's -c value — the client-side limits are what prevent the silent mid-generation cut-offs, because the model itself cannot budget its own tokens (§03).
