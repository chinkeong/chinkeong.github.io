Qwen 3.8 27B Optimal settings

How to run Qwen3.8-27B well on whatever you have — RTX 30/40/50 series, DGX Spark (GB10), Intel Arc Pro B50/B70, or a Panther Lake iGPU. Grounded in measured runs on an RTX 3090 and fact-checked against published specs and community benchmarks.

ModelQwen3.8-27B · hybrid attention
Native context262,144 tok
Q4 weights~16.5 GB
ReferenceRTX 3090 · 40 t/s measured
Benchmark run~2k in + ~100k thinking/out

01

The model, in five facts that drive every setting

  • Hybrid attention. Most of its 64 layers are Gated DeltaNet (linear attention, constant-size state); only a minority are standard attention with 4-KV-head GQA. Consequence: the KV cache is a fraction of a normal 27B's — ~3 GB at 122k with Q8 — so huge contexts are cheap in memory and speed decays gently as they fill.
  • Native 262,144 context. No YaRN or rope tricks needed below that; the limit you'll actually hit is VRAM, not the model.
  • Thinking always on, defaulting to xhigh. Reasoning tokens share the context window with your prompt and output — a 100k-token thinking run needs a >100k window (§04).
  • Vision is optional at serve time. The mmproj projector costs ~1.3 GB of VRAM; drop it for text-only work.
  • Official thinking-mode sampling: temp 1.0 · top-p 0.95 · top-k 20 · min-p 0. Clients that silently send temperature 0 (aider does) cause repetition loops — override them.

02

The physics: bandwidth is king, and VRAM is a cliff

Decode speed ≈ memory bandwidth ÷ bytes read per token. A 4-bit quant reads ~16.5 GB per token; divide your card's GB/s by that and multiply by ~0.7 (measured efficiency on CUDA) and you have your ceiling. This one ratio predicts every row of the matrix in §06.

The second law: speed vs. context is a cliff, not a curve. Flat while weights + KV fit in VRAM; ~10× collapse the moment anything spills over the PCIe bus. Measured on the reference 3090:

Corollary

Allocated ≠ used: a big window with a small prompt costs VRAM, not speed. And below the cliff, shrinking context buys nothing — there is no "optimal point" to search for.

03

Universal rules — true on every card

  • One token pool. prompt + thinking + output ≤ context. The model has no awareness of its limits and cannot budget its own thinking; limits are enforced by your config only.
  • Cut-offs are client-side. The server generates until told to stop. Truncations come from the client's max_tokens, its request timeout, or Ctrl+C — and with OpenAI-compatible APIs a cut generation cannot seamlessly resume. Size max_tokens and the client timeout so the whole run fits one response.
  • One slot, quantized KV. --parallel 1 (some UIs default to 2 = double KV) and -ctk q8_0 -ctv q8_0 (halves KV, negligible loss — but never Q4 for the K cache).
  • --no-mmap on RAM-tight machines. Otherwise the whole GGUF stays cached in system RAM even after the weights are in VRAM.
  • All layers on GPU or accept the cliff. Partial offload speed is set by CPU RAM bandwidth, not by the GPU — a 5080 and a 4060 Ti offload at nearly the same ~8–12 t/s.

04

Reasoning effort: the setting that moves hours, not percent

The default xhigh maximizes benchmark scores by thinking enormously — community testing found 22,276 reasoning tokens and 21 minutes spent on a simple SVG task that completes in ~2 minutes with reasoning off. On the other end, disabling reasoning measurably hurt complex tasks (coordinate math errors, degraded geometry). The honest guidance:

EffortUse forCost
xhigh (default)benchmarks, hardest problems, unattended runscan consume 100k+ tokens / hours
mediumeveryday coding — the sane defaultminutes, not hours
low / nonequick edits, boilerplate, chatseconds–minutes, quality dips on hard tasks

Set it server-side in llama.cpp: --chat-template-kwargs "{\"reasoning_effort\":\"medium\"}" (GUI front-ends typically expose it as a reasoning-effort setting). Keep xhigh only for runs where you'd rather wait than re-prompt.

Rule of thumb

For a benchmark, keep the quant fixed across machines (Q4-class) — a different quant is a different model. For daily use, buy the best quant your VRAM holds fully resident.

MTP speculative decoding — free speed on every GPU

Qwen3.8-27B ships with a built-in multi-token prediction (MTP) draft head, and it survives quantization — the standard K-quant GGUFs above carry it already (it's pinned to Q8_0). llama.cpp's draft-mtp path (merged July 2026) uses it to draft several tokens per step and verify them with the full model, so output quality is mathematically identical — rejected drafts are discarded. Unlike NVFP4, this works on any GPU llama.cpp supports: Ampere, Ada, Blackwell, Arc, iGPUs.

  --spec-type draft-mtp  --spec-draft-n-max 4  --spec-draft-p-min 0.75

Reported gains span +33% to +145% decode depending on hardware and workload — an RTX 5090 tester measured 148 avg / 203 peak t/s on the NVFP4 tiers with acceptance ~49%, rising with long repetitive contexts. Two hardware-dependent caveats, so benchmark on your own machine: the optimal --spec-draft-n-max varies per system (that tester found 4 fastest, while 6–8 collapsed acceptance and got slower — sweep 1–6 and keep the winner), and acceptance rates vary a lot with prompt style, so quick-test on your real workload, not a toy prompt. Requires a llama.cpp build recent enough to have the draft-mtp path.

Appendix

Connecting aider to llama-server

Every recipe above ends with an OpenAI-compatible server on port 1234 — which means aider (the terminal AI pair-programmer) connects to any of them with one identical client setup. Nothing here is hardware-specific.

Step 1 · Install aider

# needs Python 3.9+ — any one of these:
python -m pip install aider-install && aider-install   # official installer (recommended)
pip install aider-chat                                 # plain pip
uv tool install --force --python python3.12 aider-chat # uv, isolated env

Step 2 · Point aider at the server

Aider's openai/ model prefix means "any OpenAI-compatible server" — llama-server and OpenVINO Model Server both qualify. Set two environment variables (the key is required by aider; make it match the server's --api-key if you set one, otherwise any placeholder works):

# Windows (cmd / batch)                              # Linux / macOS
set OPENAI_API_BASE=http://localhost:1234/v1         export OPENAI_API_BASE=http://localhost:1234/v1
set OPENAI_API_KEY=dummy                             export OPENAI_API_KEY=dummy

Step 3 · Tell aider the model's limits

Aider knows nothing about a local model until you describe it. Create .aider.model.metadata.json in the directory you launch aider from (or your home directory). Match max_input_tokens to the server's -c value — these two numbers drifting apart is the classic silent failure:

{
    "openai/qwen/qwen3.8-27b": {
        "max_input_tokens": 122880,
        "max_tokens": 106496,
        "input_cost_per_token": 0,
        "output_cost_per_token": 0,
        "supports_vision": true
    }
}

The model name after openai/ must match what the server reports at /v1/models — llama-server sets it with --alias, so the recipes above all serve as qwen/qwen3.8-27b.

Step 4 · Fix aider's defaults for a thinking model

Aider sends temperature 0 by default — a repetition-loop trigger on reasoning models — and needs to know to strip <think> blocks before parsing edits. Create .aider.model.settings.yml next to the metadata file:

- name: openai/qwen/qwen3.8-27b
  use_temperature: 1.0
  reasoning_tag: think
  extra_params:
    top_p: 0.95

Step 5 · Launch

aider --model openai/qwen/qwen3.8-27b --edit-format diff --timeout 3600
  • --edit-format diff — the model writes only changed hunks instead of whole files. On local t/s this is the biggest quality-of-life setting there is: a 60 KB file edit drops from minutes to seconds. Diff also degrades gracefully on cut-offs (complete hunks still apply).
  • --timeout 3600 — long thinking runs outlive default client timeouts; the server log shows a timeout as "Client disconnected. Stopping generation".
  • First run sanity checks: the model-warning banner should be gone (metadata file found), and the banner should read diff edit format. If edits arrive mangled, the fallback is removing --edit-format diff to use whole-file mode.
  • Vision: with supports_vision: true and the server launched with --mmproj, you can /add screenshot.png in aider and the local model will see it.

Other clients: Qwen Code, Pi, OpenCode

The same server serves any OpenAI-compatible client — only the config file format changes. In every case the three facts to supply are the same: base URL http://localhost:1234/v1, the model id the server reports (qwen/qwen3.8-27b via --alias), and the context/output limits from your -c setting.

Qwen Code CLI · Qwen's own terminal agent

# install (Node.js 20+)
npm install -g @qwen-code/qwen-code
# configure via env vars — put them in ~/.qwen/.env to persist:
OPENAI_BASE_URL=http://localhost:1234/v1
OPENAI_API_KEY=dummy
OPENAI_MODEL=qwen/qwen3.8-27b
# then just run:
qwen

The API key must be present even for a local server ("Missing credentials" otherwise), and set the context window explicitly in its settings if offered — Qwen Code's built-in defaults assume the cloud model's limits, not your -c value. (setup notes)

Pi coding agent

# custom providers live in ~/.pi/agent/models.json:
{
  "providers": {
    "llamacpp": {
      "baseUrl": "http://localhost:1234/v1",
      "api": "openai-completions",
      "apiKey": "dummy",
      "compat": { "supportsDeveloperRole": false, "supportsReasoningEffort": false },
      "models": [
        { "id": "qwen/qwen3.8-27b", "name": "Qwen3.8 27B (local)",
          "contextWindow": 122880, "maxTokens": 106496, "reasoning": true }
      ]
    }
  }
}

The compat flags matter: they tell Pi to send a plain system role and skip the reasoning_effort request parameter — the dialect llama-server expects. Pi enforces maxTokens client-side, so size it like aider's (this is the client whose default cap causes the mid-generation cut-offs described in §03). (docs)

OpenCode

# install:  npm i -g opencode-ai   (or the curl installer / brew)
# config: ~/.config/opencode/opencode.json (or opencode.json in the project)
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "llamacpp": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "llama-server (local)",
      "options": { "baseURL": "http://localhost:1234/v1", "apiKey": "dummy" },
      "models": {
        "qwen/qwen3.8-27b": {
          "name": "Qwen3.8 27B (local)",
          "limit": { "context": 122880, "output": 106496 }
        }
      }
    }
  }
}
# run:  opencode --model llamacpp/qwen/qwen3.8-27b   (or pick via /models)

Two gotchas from the docs: baseURL must sit inside options, not at the provider root, and the provider id must be a custom name ("llamacpp", "local") — reusing a built-in provider name breaks resolution. (llama.cpp example)

One rule for all clients

Whatever the client, its context and max-output settings must match the server's -c value — the client-side limits are what prevent the silent mid-generation cut-offs, because the model itself cannot budget its own tokens (§03).
