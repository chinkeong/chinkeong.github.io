Qwen 3.8 27B Optimal settings

How to run Qwen3.8-27B well on whatever you have — RTX 30/40/50 series, DGX Spark (GB10), Intel Arc Pro B50/B70, or a Panther Lake iGPU. Grounded in measured runs on an RTX 3090 and fact-checked against published specs and community benchmarks.

ModelQwen3.8-27B · hybrid attention
Native context262,144 tok
Q4 weights~16.5 GB
ReferenceRTX 3090 · 40 t/s base · 82 t/s tuned MTP
Benchmark run~2k in + ~100k thinking/out

01

The model, in five facts that drive every setting

  • Hybrid attention. Most of its 64 layers use Gated DeltaNet, a linear-attention design whose memory use stays constant no matter how long the context gets; only a minority are standard attention layers (and those use GQA with 4 KV heads). The result: the KV cache is a fraction of a normal 27B's — about 3 GB at 122k context with a Q8 cache — so huge contexts are cheap in memory, and speed falls off gently as they fill rather than collapsing.
  • Native 262,144 context. No YaRN or rope tricks needed below that; the limit you'll actually hit is VRAM, not the model.
  • Thinking always on, defaulting to xhigh. Reasoning tokens share the context window with your prompt and output — a 100k-token thinking run needs a >100k window (§04).
  • Vision is optional at serve time. The mmproj projector costs ~1.3 GB of VRAM; drop it for text-only work.
  • Official thinking-mode sampling: temp 1.0 · top-p 0.95 · top-k 20 · min-p 0. Clients that silently send temperature 0 (aider does) cause repetition loops — override them.

02

The physics: bandwidth is king, and VRAM is a cliff

Generation speed comes down to one ratio: how fast your card can read memory, divided by how much it must read per token. Every token requires reading the entire model — about 16.5 GB for a 4-bit quant. So take your card's bandwidth in GB/s, divide by 16.5, multiply by ~0.7 (the efficiency we measured on CUDA), and that's your speed ceiling in tokens per second. This one calculation predicts every row of the matrix in §06.

The second law: speed vs. context is a cliff, not a curve. Flat while weights + KV fit in VRAM; ~10× collapse the moment anything spills over the PCIe bus. Measured on the reference 3090:

Corollary

Allocated is not the same as used: a big context window with a small prompt in it costs VRAM, not speed. And as long as you stay below the cliff, shrinking the window gains you nothing — there is no hidden "optimal point" to search for.

03

Universal rules — true on every card

  • One token pool. prompt + thinking + output ≤ context. The model has no awareness of its limits and cannot budget its own thinking; limits are enforced by your config only.
  • Cut-offs are client-side. The server generates until told to stop. Truncations come from the client's max_tokens, its request timeout, or Ctrl+C — and with OpenAI-compatible APIs a cut generation cannot seamlessly resume. Size max_tokens and the client timeout so the whole run fits one response.
  • One slot, quantized KV. --parallel 1 (some UIs default to 2 = double KV) and -ctk q8_0 -ctv q8_0 (halves KV, negligible loss — but never Q4 for the K cache).
  • --no-mmap on RAM-tight machines. Otherwise the whole GGUF stays cached in system RAM even after the weights are in VRAM.
  • All layers on GPU or accept the cliff. Partial offload speed is set by CPU RAM bandwidth, not by the GPU — a 5080 and a 4060 Ti offload at nearly the same ~8–12 t/s.

04

Reasoning effort: the setting that moves hours, not percent

The default xhigh maximizes benchmark scores by thinking enormously — community testing found 22,276 reasoning tokens and 21 minutes spent on a simple SVG task that completes in ~2 minutes with reasoning off. On the other end, disabling reasoning measurably hurt complex tasks (coordinate math errors, degraded geometry). The honest guidance:

EffortUse forCost
xhigh (default)benchmarks, hardest problems, unattended runscan consume 100k+ tokens / hours
mediumeveryday coding — the sane defaultminutes, not hours
low / nonequick edits, boilerplate, chatseconds–minutes, quality dips on hard tasks

Set it server-side in llama.cpp: --chat-template-kwargs "{\"reasoning_effort\":\"medium\"}" (GUI front-ends typically expose it as a reasoning-effort setting). Keep xhigh only for runs where you'd rather wait than re-prompt.

Rule of thumb

For a benchmark, use the same quant on every machine (Q4-class) — a different quant is a different model and its scores aren't comparable. For daily use, pick the best quant that fits entirely in your VRAM.

MTP speculative decoding — free speed on every GPU

Qwen3.8-27B ships with a built-in multi-token prediction (MTP) draft head — a small helper network that guesses several tokens ahead so the full model only has to check them, which is much faster than generating each one. The standard K-quant GGUFs above already include it (the head itself always stays at 8-bit, whatever the main quant). llama.cpp added support in July 2026, and because every guess is verified by the full model before it's accepted, the output is exactly what the model would have written anyway — you only gain speed. It works on any GPU llama.cpp supports: Ampere, Ada, Blackwell, Arc, iGPUs.

  --spec-type draft-mtp  --spec-draft-n-max 4  --spec-draft-p-min 0.75

How much speed it adds depends heavily on hardware and workload — reports range from +33% to +145%. An RTX 5090 tester saw 148 avg / 203 peak t/s on the NVFP4 tiers. On our reference 3090, generation went from 40.3 to 58–60 t/s — +45% at the default-ish settings, with 89% of drafted tokens accepted, and a proper settings sweep pushed it much further (see the tuning section below). The warning both numbers carry: benchmark on your own machine. That 5090 tester found n-max 4 fastest with 6–8 slower; our 3090 kept getting faster all the way to n-max 10. The two machines genuinely disagree — there is no universal best value. You'll need a llama.cpp build recent enough to have the draft-mtp feature.

DFlash2 — block drafting (PR stage)

DFlash2 drafts differently from MTP: instead of guessing one token at a time, it predicts a whole 7-token block in a single pass, then picks the most plausible sequence out of the candidates it considered for each position. Like MTP, every draft is verified before it's accepted, so the output is identical to running the model alone. The costs: a separate 1.14 GB drafter model to download (incoai/Qwen3.8-27B-DFlash2-GGUF, ~1.2 GB of VRAM), and — until llama.cpp PR 27342 is merged — building llama.cpp yourself from that branch.

That table says two things. First, speculation gets a 3090 to ~70 t/s — the 100k reference run drops from 45 to under 26 minutes, which matches what this guide estimates for an RTX 5090 without speculation (and the sweep below pushed it further still). Second, the NVFP4 rows show that the quant and the drafter interact: speculative decoding makes the GPU check several drafted tokens at once, and that batch-checking is exactly the work NVFP4's software fallback does slowest. So on cards older than Blackwell, pair speculation with normal K-quants, not NVFP4.

Tuning the drafter — an 18-config sweep on the 3090

The table above used the settings each method's authors recommend. Then we swept --spec-draft-n-max across both methods (same prompt, temp 0, warm cache — numbers run a few t/s hotter than the cold-start table, so compare within this chart, not against it). The result contradicted both recommendations:

Three findings, all measured 2026-08-21:

  • The tuned built-in MTP head wins outright on this card: n-max 10 with p-min 0.5 gives 81.7 t/s — +105% over baseline, beating DFlash2's best (77.6 at n-max 4–5). No drafter download, no source build, no VRAM cost.
  • --spec-draft-p-min is the hidden second knob. At n-max 10, lowering it from 0.75 to 0.5 was worth +8 t/s (73.5 → 81.7); at n-max 4 the difference was small. A high confidence floor keeps pausing exactly the long drafts that big n-max exists for.
  • DFlash2's recommended n-max 7 was not its own best setting here — 4 and 5 both beat it (77.6/77.5 vs 74.0). Every recommendation in this space, including ours, is one machine's measurement.
Reading acceptance tables

Published speculative-decoding tables (like the DFlash2 blog's "mean acceptance length") are speed numbers, not quality scores. The verify step guarantees every configuration writes exactly what the base model would have written — a higher acceptance number just means more tokens got through per check. Quality only changes when the weights change (a different quant); speed only changes when the drafter changes.

Does FP4 beat INT4? A scored comparison

A common belief says floating-point formats always beat integer formats at the same bit width. We tested it: the three quants above, graded for correctness on GSM8K and MATH-500 (20 problems each, greedy decoding, identical prompts, 4096-token budget; answers that ran out of budget mid-thinking count as wrong and are reported as truncations). Measured on the reference 3090:

QuantFormatGSM8KMATH-500Decode (MTP on)Draft accept len
Q4_K_MK-quant (integer grid)85% (1 trunc)75% (5 trunc)63–70 t/s4.7–4.9
NVFP4-HIGHFP4, most extras upgraded85% (1 trunc)65% (5 trunc)~55 t/s4.7–4.8
NVFP4-VERY-LOWFP4, smallest tier85% (0 trunc)65% (5 trunc)~49 t/s3.33

What the numbers say:

  • "Floating point always wins" did not survive the test. All three tied on GSM8K; on MATH-500 the integer-grid K-quant answered two more problems than either FP4 file. At 20 samples that edge is weak evidence — but it is the opposite direction from the belief. What actually decides 4-bit quality is how cleverly a format spends its bits — block sizes, scale precision, which layers stay high-precision — and mature K-quants are very good at that game. Both families use fine-grained scaling; the float-vs-integer grid underneath matters far less than people assume.
  • The two NVFP4 tiers scored identically — expected once you know the family shares one byte-identical NVFP4 backbone, with tiers differing only in the surrounding layers. The surprise is where VERY-LOW's savings actually landed: its MTP draft head drafts noticeably worse (acceptance length 3.33 vs ~4.8), so the cheap tier costs you speculative-decoding speed, not accuracy.
  • Sample-size honesty: each problem is worth 5 points. Every gap in this table is one or two questions wide. Treat it as "no meaningful quality difference, mild edge to the K-quant" — not a ranking. We also ran the same prompts through a different serving stack and grader version and saw individual cells move by up to 10 points, which means measurement variance is the same size as the differences being measured. Anyone showing you a one-run quant ranking without error bars is selling something.
The takeaway

Pick your file by size and speed, not by format ideology: on a 24 GB Ampere card that means Q4_K_M (fastest, best-drafting MTP head, and the mild quality edge is on its side too). NVFP4's real advantages live on Blackwell hardware where the format runs natively.

Appendix

Connecting aider to llama-server

Every recipe above ends with an OpenAI-compatible server on port 1234 — which means aider (the terminal AI pair-programmer) connects to any of them with one identical client setup. Nothing here is hardware-specific.

Step 1 · Install aider

# needs Python 3.9+ — any one of these:
python -m pip install aider-install && aider-install   # official installer (recommended)
pip install aider-chat                                 # plain pip
uv tool install --force --python python3.12 aider-chat # uv, isolated env

Step 2 · Point aider at the server

Aider's openai/ model prefix means "any OpenAI-compatible server" — llama-server and OpenVINO Model Server both qualify. Set two environment variables (the key is required by aider; make it match the server's --api-key if you set one, otherwise any placeholder works):

# Windows (cmd / batch)                              # Linux / macOS
set OPENAI_API_BASE=http://localhost:1234/v1         export OPENAI_API_BASE=http://localhost:1234/v1
set OPENAI_API_KEY=dummy                             export OPENAI_API_KEY=dummy

Step 3 · Tell aider the model's limits

Aider knows nothing about a local model until you describe it. Create .aider.model.metadata.json in the directory you launch aider from (or your home directory). Match max_input_tokens to the server's -c value — these two numbers drifting apart is the classic silent failure:

{
    "openai/qwen/qwen3.8-27b": {
        "max_input_tokens": 122880,
        "max_tokens": 106496,
        "input_cost_per_token": 0,
        "output_cost_per_token": 0,
        "supports_vision": true
    }
}

The model name after openai/ must match what the server reports at /v1/models — llama-server sets it with --alias, so the recipes above all serve as qwen/qwen3.8-27b.

Step 4 · Fix aider's defaults for a thinking model

Aider sends temperature 0 by default — a repetition-loop trigger on reasoning models — and needs to know to strip <think> blocks before parsing edits. Create .aider.model.settings.yml next to the metadata file:

- name: openai/qwen/qwen3.8-27b
  use_temperature: 1.0
  reasoning_tag: think
  extra_params:
    top_p: 0.95

Step 5 · Launch

aider --model openai/qwen/qwen3.8-27b --edit-format diff --timeout 3600
  • --edit-format diff — the model writes only changed hunks instead of whole files. On local t/s this is the biggest quality-of-life setting there is: a 60 KB file edit drops from minutes to seconds. Diff also degrades gracefully on cut-offs (complete hunks still apply).
  • --timeout 3600 — long thinking runs outlive default client timeouts; the server log shows a timeout as "Client disconnected. Stopping generation".
  • First run sanity checks: the model-warning banner should be gone (metadata file found), and the banner should read diff edit format. If edits arrive mangled, the fallback is removing --edit-format diff to use whole-file mode.
  • Vision: with supports_vision: true and the server launched with --mmproj, you can /add screenshot.png in aider and the local model will see it.

Other clients: Qwen Code, Pi, OpenCode

The same server serves any OpenAI-compatible client — only the config file format changes. In every case the three facts to supply are the same: base URL http://localhost:1234/v1, the model id the server reports (qwen/qwen3.8-27b via --alias), and the context/output limits from your -c setting.

Qwen Code CLI · Qwen's own terminal agent

# install (Node.js 20+)
npm install -g @qwen-code/qwen-code
# configure via env vars — put them in ~/.qwen/.env to persist:
OPENAI_BASE_URL=http://localhost:1234/v1
OPENAI_API_KEY=dummy
OPENAI_MODEL=qwen/qwen3.8-27b
# then just run:
qwen

The API key must be present even for a local server ("Missing credentials" otherwise), and set the context window explicitly in its settings if offered — Qwen Code's built-in defaults assume the cloud model's limits, not your -c value. (setup notes)

Pi coding agent

# custom providers live in ~/.pi/agent/models.json:
{
  "providers": {
    "llamacpp": {
      "baseUrl": "http://localhost:1234/v1",
      "api": "openai-completions",
      "apiKey": "dummy",
      "compat": { "supportsDeveloperRole": false, "supportsReasoningEffort": false },
      "models": [
        { "id": "qwen/qwen3.8-27b", "name": "Qwen3.8 27B (local)",
          "contextWindow": 122880, "maxTokens": 106496, "reasoning": true }
      ]
    }
  }
}

The compat flags matter: they tell Pi to send a plain system role and skip the reasoning_effort request parameter — the dialect llama-server expects. Pi enforces maxTokens client-side, so size it like aider's (this is the client whose default cap causes the mid-generation cut-offs described in §03). (docs)

OpenCode

# install:  npm i -g opencode-ai   (or the curl installer / brew)
# config: ~/.config/opencode/opencode.json (or opencode.json in the project)
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "llamacpp": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "llama-server (local)",
      "options": { "baseURL": "http://localhost:1234/v1", "apiKey": "dummy" },
      "models": {
        "qwen/qwen3.8-27b": {
          "name": "Qwen3.8 27B (local)",
          "limit": { "context": 122880, "output": 106496 }
        }
      }
    }
  }
}
# run:  opencode --model llamacpp/qwen/qwen3.8-27b   (or pick via /models)

Two gotchas from the docs: baseURL must sit inside options, not at the provider root, and the provider id must be a custom name ("llamacpp", "local") — reusing a built-in provider name breaks resolution. (llama.cpp example)

One rule for all clients

Whatever the client, its context and max-output settings must match the server's -c value — the client-side limits are what prevent the silent mid-generation cut-offs, because the model itself cannot budget its own tokens (§03).
