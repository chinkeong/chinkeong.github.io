Ultracode at max effort: one 30-hour run, audited

Claude Code with Opus 5.5 at effort max and ultracode on built one single-file aquarium from one prompt. It worked for 30 hours 30 minutes with no human message. Then the user asked it to wrap up, and the turn ended 92 seconds later, after 30 hours 32 minutes. It ran 7 workflows and 122 subagent runs, and it processed 5.06 billion tokens. 1. What ultracode is

Ultracode is a working mode of Claude Code. With it on, the main model does not do the work alone. It becomes an orchestrator. It writes small programs, called workflows, that start many helper agents, check their output with other agents, and collect the results.

In this session the user turned it on through the /effort command. Claude Code answered: "Set effort level to max (this session only) … · Ultracode on". From then on, Claude Code added this instruction to the model's context cited:

Ultracode is on: optimize for the most exhaustive, correct answer — not the
fastest or cheapest. Use the Workflow tool on every substantive task; token
cost is not a constraint. See the Ultracode section and quality patterns in
the workflow authoring reference. Solo only on conversational/trivial turns.

Ultracode and effort are two separate settings in the same command. Ultracode decides the shape of the work: how many agents, how many workflows, how much checking. Effort decides how deeply each single model request thinks. A user can also turn ultracode on for one message only, by writing the word "ultracode" in the prompt. This audit page was made that way.

Plain words

Orchestrator
The main model loop that talks to the user. In ultracode it plans, writes workflow scripts, fixes shared code and decides what runs next.
Workflow
A short JavaScript program written by the orchestrator. It starts subagents, runs them in parallel or as a pipeline, and returns their results as structured data.
Subagent
A separate model session with its own context and tools. It gets one job, for example "build the jellyfish module" or "try to prove this finding wrong".
Round
One step of building or fixing in which many agents work at the same time. This session had a build round, a polish round and 2 fix rounds.
Lens
One point of view in a review: requirements, performance, robustness, visual, motion or code.
Verifier
A subagent whose job is to refute another agent's claim by reproducing it. Only findings the verifier reproduces count as confirmed.
Frozen build
A copy of the product that nobody may edit while a review runs, so that every line number in a finding stays valid.
Token
A piece of a word. Models read and write in tokens.
Thinking tokens
Tokens the model writes to reason before it acts. They are billed as output but are not shown.
Cache read
Input that the model has already seen in this conversation. It is read from a cache at 5% of the normal input price.

The full prompt 
# Animated Aquarium -- LLM Prompt

Create a single self-contained HTML file that renders an animated
deep-ocean aquarium. Requirements:

## File constraints

1. One file only. All CSS and JavaScript inline. No external
   resources of any kind: no CDN links, no images, no fonts, no
   network requests. The page must work offline when opened from a
   local file.
2. Draw the scene on a canvas element that always fills the browser
   window and re-adapts when the window is resized, with no
   stretching artifacts and no scrollbars.

## CONFIG object

All tunable parameters must be named constants in one CONFIG object
at the top of the script so a reader can adjust them. Include at
minimum:

- Fish count per species
- Speed multiplier (global, affects all creatures)
- Bubble spawn interval in milliseconds
- Jellyfish count
- Crab count
- Maximum simultaneous bubbles
- Day/night cycle duration in seconds (0 to disable)

## Sea creatures (required)

Implement at least the following. Each must be visually distinct
(different shape, color, and drawing logic) and have its own
movement behavior. Be creative with the exact appearance -- the
descriptions below are guidelines, not pixel specs.

### Fish -- at least 3 species, at least 2 of each

1. **Tropical fish** -- oval body, warm palette (oranges, yellows,
   whites), horizontal stripes or bands. Movement: steady horizontal
   glide, reverses direction at canvas edges, slight vertical drift.

2. **Angelfish** -- tall diamond or kite-shaped body, elongated
   dorsal and ventral fins, cool palette (blues, purples, silvers).
   Movement: slower horizontal travel with a pronounced sinusoidal
   vertical bob. The difference from species 1 must be obvious
   within seconds.

3. **Small schooling fish** -- tiny, simple silhouettes that move as
   a loose school. They should loosely follow a shared heading that
   slowly rotates, with each individual adding small random offsets
   so the group shimmers rather than moving rigidly. At least 8 in
   the school.

### Jellyfish -- at least 2

Translucent, bell-shaped bodies with trailing tentacles. The bell
should visibly pulse (expand/contract) to propel the jellyfish
upward; between pulses it drifts slowly downward and sideways.
Tentacles should sway and trail behind the movement. Use
semi-transparent fills so the jellyfish look ghostly and
luminescent. They move independently of fish.

### Bottom dwellers

4. **Crab** -- at least 1. Sits on the sandy floor. Occasionally
   scuttles sideways in short bursts, pauses, then scuttles again.
   Draw with a round body, eyestalks, and visible claws/pincers.

5. **Lobster** -- at least 1. Larger than the crab, reddish-brown,
   with a segmented tail, large front claws, and antennae. Moves
   slowly along the bottom, occasionally stops and raises its claws.

6. **Starfish** -- at least 1. Five-armed, textured, resting on the
   floor or on a rock. Moves extremely slowly (almost imperceptibly)
   or stays still. Subtle color -- ochre, rust, or muted purple.

### Seahorse -- at least 1

Upright posture, curled tail, snout. Bobs vertically in place or
drifts very slowly. Tail may curl and uncurl gently.

### Sea turtle -- at least 1

Distinct shell pattern (hexagonal or scute pattern drawn on the
shell). Flippers animate in a slow rowing stroke. Moves gracefully
across the scene at a leisurely pace, occasionally changing
direction in gentle arcs, not sharp turns.

## Shells and static sea floor objects

- **Seashells** -- at least 3 different shells scattered on the
  floor: a spiral conch, a scallop/fan shape, and a small cowrie or
  similar. Give each a slightly different size and tint.
- **Coral formations** -- at least 2 clusters of branching or
  brain coral near the bottom, with warm pinks, oranges, or reds.
- **Sea anemone** -- at least 1, with a cluster of waving tentacles
  rooted to a rock or the floor. Tentacles sway gently with
  a current-like motion.
- **Seaweed / kelp** -- at least 3 stalks of different heights that
  sway gently, rooted at the bottom. Vary the green hue per stalk.
- **Rocks** -- a few rounded stones of varying sizes on the floor.

## Bubbles

Bubbles appear near the bottom, rise to the top with gentle
side-to-side wobble, and keep respawning indefinitely. They should
look translucent with a subtle specular highlight. Slight size
variation.

## Environment and atmosphere

- **Water background** -- a vertical gradient from dark deep blue at
  the top to a lighter teal-blue near the bottom, suggesting depth.
- **Caustic light rays** -- subtle, slow-moving shafts of pale light
  from the surface, barely visible. They add atmosphere without
  overwhelming the scene.
- **Sandy floor** -- a textured strip at the bottom with slight
  undulation, small pebbles, and a warm sandy color.
- **Particle motes** -- optional: tiny floating specks drifting
  slowly in the water to suggest organic matter. Very subtle.
- **Day/night cycle** (optional but encouraged) -- if enabled in
  CONFIG, the overall scene brightness slowly oscillates between
  a brighter daytime palette and a darker nighttime palette. During
  "night" jellyfish and certain fish could glow faintly.

## Movement rules

- All creatures must remain visible: turn, wrap, or bounce at canvas
  edges.
- Each species must have a clearly distinct movement pattern. A
  viewer should be able to tell species apart by movement alone
  within 15 seconds.
- Creatures should not cluster in one area. Distribute them across
  the tank.
- Bottom dwellers stay on the floor. Jellyfish occupy the upper
  half. Fish and turtle roam the middle. Seahorse stays near decor.

## Creative freedom

The descriptions above set a minimum. You are encouraged to add:

- Additional species or variants (pufferfish, manta ray, eel,
  clownfish in an anemone, etc.)
- Decorative details (sunken treasure chest, ship wheel, anchor,
  ceramic diver figurine, etc.)
- Interaction touches (fish avoiding each other, schooling fish
  reacting to edges, crab retreating when a fish swims near)
- Ambient effects (ripple overlay on the surface, shadow on the
  floor, depth-of-field blur for distant fish)
- Sound-reactive elements if the Web Audio API is available

Surprise me. The goal is a beautiful, living aquarium that someone
would leave open as a desktop decoration.

## Quality

- The page must produce no console errors.
- Animation should be smooth at 60 fps on a mid-range machine. Use
  requestAnimationFrame, delta-time, and avoid unnecessary
  allocations in the render loop.
- All drawing must use the Canvas 2D API (no WebGL required, but
  allowed as a bonus layer).

Output only the complete HTML file content, starting with
`<!DOCTYPE html>`. No explanations, no markdown fences, no extra
text.

3. Effort: xhigh against max

Effort mainly sets how deeply each model request thinks. It can also change how many tool calls an agent makes. It does not set how many agents or workflows run. That is ultracode's job.

What the documentation says

  • On Opus 5.5, thinking is always on. A fixed thinking budget (budget_tokens) is rejected with an error. Effort is the main control. A line in the system prompt can reduce thinking further. cited
  • There are five levels: low, medium, high, xhigh, max. For Opus 5.5 the API default is medium. The guide says to start at medium and to "reserve xhigh and max for work where you have measured a quality gain". cited
  • The Opus 5.5 guide says "max is uncapped", and that Opus 5.5 "tends to think more per turn than Claude Opus 5, especially at xhigh and max". cited
  • The older Opus 4.7 guide calls xhigh "the best setting" for "most coding and agentic use cases" and says Claude Code used it as its default. It says max "may show diminishing returns from increased token usage" and "can be prone to overthinking". The Opus 5.5 guide does not repeat these lines. cited
  • Every response has a hard output limit, max_tokens. On Opus 5.5 the largest value for a normal request is 128,000 tokens, and thinking counts toward it. cited

Is there a kilobyte limit on thinking at xhigh?

No fixed limit is documented for xhigh. Effort is a setting for how much the model chooses to think, not a quota. So xhigh does not stop at a set number of kilobytes. On average it simply thinks less than max. The guide calls max "uncapped". The one hard limit, the same for every effort level, is the 128,000-token output limit of a single response. That is roughly 450 to 510 KB of English text estimate, at 3.5 to 4 characters per token. In this run, requests reached that limit and were cut off 6 times.

What max effort did in this run

The logs record the thinking tokens of almost every request measured. Across 15,337 requests the model wrote at least 13,766,555 thinking tokens. That is 58.6% of all output tokens. (147 requests, about 1%, were logged without a final count. One of them is a 128,000-token cut-off. So the totals are slightly low.) Most requests thought briefly: the median was 232 thinking tokens, and 90% of requests stayed at or under 1,862. A few thought for a very long time. The 16 requests above 64,000 thinking tokens are 0.1% of requests, but they hold 11.3% of all thinking.

There were 6 cut-offs. Five are logged with the max_tokens stop reason, and one more appears only as a Claude Code notice ("Output token limit hit"). All of them happened in Phase 1, between 16:19 and 17:03. In each case a builder agent had just read the engine and tried to plan its whole module in one think. How effort affects the duration

Thinking took 39.3 hours of the 136.6 agent-hours, or 28.8% measured. The rest was writing code and waiting for tools: builds, headless Chrome runs and long motion simulations. Several of the longest agents were slow because of their tests, not their thinking. For example, one polish agent ran for 224 minutes, and three of its commands hit the 600-second timeout. Effort can also change the number of tool calls, and the documentation gives no number for that, so the forecast below changes only the thinking.

Phase 0 · 15:18–15:57 · The orchestrator builds the base alone

Before any agent started, the orchestrator built what every agent would share. It checked the machine: Node 24, Chrome 154 and an RTX 3090. Then it thought for 7 minutes in one request, about 40,000 tokens, which was the longest think of the main loop. It wrote shoot.mjs, a tool that drives a hidden (headless) Chrome browser. With it, every agent could take screenshots of its own work and read the browser console. Next it wrote the engine: the CONFIG object, the core (random numbers, sprites, depth, layout), the environment (water, sand, light, bubbles, night) and a build script that joins all parts into one HTML file. It wrote a reference module and AGENT_BRIEF.md, a 13 KB contract for all module authors with 7 hard performance rules. Last, it tuned a shared rock painter over 4 screenshot rounds, so that every agent would draw rocks the same way.

Phase 2 · 21:37–00:24 · Integration, then WF2 fixes the lost issues

The orchestrator joined all 10 groups into one tank for the first time. The console was silent and modules used about 1.9 ms per frame, but the first frames froze for 1.8 seconds. It recorded a CPU profile, tested the groups one by one, and found that rock sprites painted on the GPU caused most of the freeze. It changed the engine to paint sprites on the CPU and copy them to the GPU once. The freeze fell from 1,795 ms to 775 ms. It then read the workflow journal and found its own truncation fault. By its count, 71 critic issues had not reached a polish agent in full. (An exact re-count for this page gives 72: 62 never arrived and 10 arrived cut off.) It wrote one input file per group and started the polish round (WF2).

Phase 3 · 00:24–02:19 · WF3: global adversarial review

The orchestrator froze the build and made no source edits until the review ended, so that every line number in a finding stayed valid. Six finder agents each examined the whole tank through one lens. Each finder passed its list to its own verifier, who was told to try hard to refute every finding by reproducing it. Verifiers wrote their own test scripts instead of reusing the finder's.

The only blocker was performance. The JavaScript needed only 2.2 ms per frame, but Chrome's GPU process replayed about 670 path fills and strokes every frame. The tank ran at 50 fps at 1920×1080 with 2× pixel density. On slower CPU cores it ran at 49.5 fps at 1600×900 and 41.8 fps at 1920×1080 with 1× pixel density. Other confirmed findings: pressing M twice left the microphone recording; after a GPU reset the tank stayed black; one tuning value turned every schooling fish into NaN; crabs got trapped against the glass in 6 of 72 tanks; setting the schooling count to 0 still showed 24 fish.

Phase 4 · 02:19–08:50 · Engine fixes, then WF4: fix, verify, re-fix

The orchestrator fixed the engine-level findings itself in 15 minutes: a new CONFIG layout, core patches, a rewritten environment, the microphone leak and the N key. It adopted the review's GPU-measuring script as tools/gpucost, sent each module finding to the group that owned it, and started fix round 1. Each group ran as a small loop: the owner fixes, an independent verifier (told not to edit) checks, and only a failed check starts a re-fix.

The verifiers also found real problems. In one group the owner had reported the trapped-crab bug as fixed; the verifier measured 25 of 144 crab tracks still stuck for over a minute. In two groups a fix had created a new problem. Verifiers also corrected at least 8 owner claims of gains that they could not reproduce, in 6 of the 10 groups. For example, the tropical-fish owner reported 63% less extra GPU-thread cost at 4K, and the verifier measured 29% to 41%. After this round the orchestrator measured the whole tank. At 1920×1080 with 2× pixel density on slower cores the frame rate rose from 26.4 to 55.3 fps, but the new build drew that size at a capped 3.6 megapixels. The release candidate, measured at 17:54 before the release gate, drew it at full resolution and ran at 54.2 fps measured.

Phase 5 · 08:50–11:46 · WF5: final acceptance review

The same six lenses ran again on a new frozen build. This time each finder also re-checked the earlier findings in its own lens (46 in total across the six lenses) and looked for problems caused by the fixes.

The GPU blocker was confirmed fixed. At 1920×1080 with 2× pixel density the GPU main thread went from 95% busy to 36%, but the new build drew that window at a capped 3.6 megapixels. At full 4K resolution it went from about 98% to 47–48%, so the code changes alone about halved the GPU work. Seven of the 8 regressions came from the engine patch that the orchestrator wrote itself between 02:24 and 02:29, which no verifier checked. Only one, a sudden speed jump of the angelfish, came from a module owner. The pattern repeats in this run: fixes create a smaller number of new problems, and only a new independent review finds them.

Phase 6 · 11:46–17:52 · Pacing rewrite, then WF6: fix round 2

The orchestrator rewrote the frame pacing and the adaptive-quality governor itself, so that a quality step is kept only if it measurably helps. It tested the result on simulated 30, 48, 100, 144 and 165 Hz screens. It also added three read-only engine functions (swimSnap, bubbleRoom, devicePx) that modules could use instead of reading the engine's internal data. Then 9 module owners fixed 23 assignments of 8 findings.

Results with numbers: the angelfish's largest speed jump fell from 221–250 to 9.5–13.2 px/s. Tropical fish that snapped back and forth after a cursor swipe fell from 29 of 288 fish reactions (72 swipes) to 0. Jellyfish had crowded the middle third of the screen (16% / 57% / 26% of time in the left, middle and right thirds); after the fix the split was 28% / 33% / 39%.

Phase 7 · 17:52–20:38 · WF7: release gate

The orchestrator ran the static check, the 18-case smoke test and GPU measurements, then froze a release candidate. Its first gate script was broken: the shell had run the back-quoted text inside the prompts as commands, so the prompts came out empty. It noticed, rewrote the script with the file editor, and started the gate at 17:59.

The major finding: under short bursts of background load, the quality governor lowered the resolution step by step and did not recover. In 3 of 4 runs the tank fell from 1600×900 to 960×540. The minor findings included a seahorse drawn behind the sea fan's lace, a regression caused by an earlier kelp fix.

Phase 8 · 20:38–21:57 · The orchestrator finishes alone

No more agents ran. The orchestrator fixed all 12 findings itself and checked almost every fix with the reviewers' own test scripts. At 20:57 its context reached 967,942 tokens and Claude Code compacted it automatically to 15,164 tokens; work continued from the summary. It caught mistakes in its own checks. First, its parser read the wrong key. Second, a reviewer's resize probe ran on the old build, because the orchestrator's file-name change did not apply. The same probe also computed an old scaling formula, so the orchestrator checked that fix with screenshots instead. The last large change split the work after a window resize into small steps. The worst frame after a 4K resize fell from 66.7–83.5 ms to 16.8–16.9 ms measured. Then it ran the final static check (pass) and the smoke test (18 of 18 clean). An edge-case set was still running at delivery: 29 of 32 cases were done and clean, and all 32 were clean at 21:57. Section 8 shows how the run ended.

What went wrong in the process

The process had faults too. An audit should show them. Each item comes from the logs measured; the dollar figures are derived.

  • The WF1 script cut critic reviews to 9,000 characters. 72 of the 109 issues did not reach a polish agent in full: 62 were missing and 10 were cut mid-text. The orchestrator counted 71, found the fault and ran a polish round ($202).
  • The same cut came back in the fix rounds. Re-fix prompts kept only the first 8,000 (WF4) or 7,000 (WF6) characters of the verifier's report. All 4 reports were longer, and in 2 of the 4 re-fixes the list of remaining problems was missing completely.
  • At max effort, build agents hit the 128,000-token output limit 6 times while still thinking, and had to plan again. Cost: about 768,000 output tokens.
  • The plan's usage limit stopped 10 agents between 03:12 and 03:14. The restart lost their conversations: about $106 and 18 minutes of idle time.
  • Agents counted up to 338 Chrome processes at once (this count may include the user's own browser). The CPU was often at 100%, and agents had to repeat timing runs and use median values.
  • Shell quoting broke a script or a patch at least 6 times, including gate.mjs, gpucost.mjs and the first release-gate script. Each time, the orchestrator noticed and rewrote the file with the editor before any agent ran with bad input.
  • The orchestrator's own engine patch before fix round 1 was never checked by a verifier. It caused 7 of the 8 regressions that the Phase 5 review found.
  • By design, re-fix results were not checked by a second verifier inside the same workflow. The orchestrator's final 12 fixes were checked only by the orchestrator itself.

Why cache reads are so large

A model has no memory between requests. Each request sends the whole conversation so far: the instructions, every file read and every tool result. An agent that makes 300 requests with a 300,000-token context reads about 90 million tokens. Prompt caching makes these repeat reads cheap, at 5% of the normal input price. Without caching, the 4.92 billion cache-read tokens would cost about $19,700 at the full input price derived. This is also why lower effort saves less money than you may expect: the largest cost grows with the number of requests and the length of each context, not with thinking.

This run was not billed per token. Between 03:12 and 03:14, all 10 running agents stopped with the message "You've hit your session limit · resets 3:30am". That message comes from a Claude subscription plan. So the user paid the plan fee, and the run used up the plan's limit once. When to use it, and how to control it

  • Use ultracode for a single deliverable where mistakes are expensive and the work can be checked by running it. Do not use it for small edits or questions.
  • The Opus 5.5 guide says to start at medium and to use xhigh or max only where a test shows a quality gain (section 3). For a long coding run like this one, test xhigh before max.
  • Set a token budget in the prompt, for example +5M. Claude Code's workflow reference describes this as a hard ceiling: once the turn has spent that many output tokens, workflows cannot start new agents cited. This run used 23.5 M output tokens.
  • Write the stop rule into the prompt, for example: "stop after a release gate with no major findings". Without it, the orchestrator decides.
  • Ask for the orchestrator's own engine changes to be checked by a verifier too. In this run, its unchecked patch before fix round 1 caused 7 of the 8 regressions that the next review found.
  • Read the status message at the end of each workflow. That is the natural point to stop or redirect, and this run had 7 of them.
  • Save the source. The session's source tree lives in a temporary folder that can be deleted.

So, dynamic or hard-coded?

  • Not hard-coded in Claude Code. Neither the tool descriptions, the ultracode reminder nor the workflow reference names a count for any task. The reference is a skill of patterns. Its numbers are examples: 3 skeptics in the adversarial-verify code, 3–5 votes for "be comprehensive", 2 empty rounds in the loop-until-dry code, 10 in a loop-until-count example.
  • Decided at run time, twice. First by the orchestrator when it wrote each script: the 10 groups follow the 10 module files it planned in Phase 0, and the lens lists are its own. Its visible messages state each shape at launch ("six independent lenses … each followed by a skeptical verifier"; "3 lenses … each followed by a refuting verifier") but give no reason for the numbers. Second, by the results inside the script: skipped refuters, conditional re-fixes and automatic re-runs.
  • Only the safety caps are fixed numbers. This run never reached them. At most 10 agents ran at once in any workflow, against a cap of 16 on this 20-thread CPU derived, and the largest workflow had 33 runs, against 1,000. No agent waited for a free slot; the only delay was the usage-limit pause in WF4 measured.
  • The size guideline. The tool text in this session asks for fewer than 10 agents per workflow unless the user's prompt calls for a different scale. Only WF7 (6 runs) stayed under 10; the others had 10 to 33 runs. The logs do not keep the tool text the model saw on 4 and 5 October, so this page cannot say whether the same guideline was in force then. If it was, six of the seven workflows went past it; as a guideline, it stops nothing.
  • Saved workflows are the exception. The Workflow tool can also run a predefined workflow by name ("built-in or from .claude/workflows/"), and such a script can fix its own counts. This run used none: all 7 scripts were written during the run, for this task.

How to steer it. Because the counts are the orchestrator's choice, the prompt is the place to set them:

  • Turn ultracode on for one message by writing "ultracode" in it, or for the session with /effort, as in this run.
  • Cap the spend with a budget such as +5M. It is a hard ceiling: once the turn has spent that many output tokens, workflows cannot start new agents.
  • Raise or remove the size guideline with "Dynamic workflow size" in /config.
  • Name the shape you want: "3 refuters per finding", "repeat the review until two rounds find nothing new", "use lower effort for builders and max only for verifiers", "send a verifier your own engine patches too". The orchestrator writes such requests into the script; nothing else will.

On Windows a file that a process still has open cannot be deleted. When Chrome's crash handler, network or GPU processes still held a file, such as the crash metrics file or the HTTP cache, the delete stopped part-way and the error was dropped. 34–35% of the leftover shared-tool folders still hold the crash metrics file, so their delete stopped at or before it. One sampled folder shows signs that the delete never ran at all measured. The GPU cost tool had the same code with a 1,500 ms timer, and agents copied it at least 9 times into their own launchers. Nothing counted or swept the folders. The orchestrator's checks at 08:50 and 17:53 looked only for live Chrome processes. After WF1 it found 172 leftover profiles and deleted them by hand, but it did not fix the tool, and from then on no one looked again.

B.5 What this has to do with ultracode

  • Disk use grew with parallel testing. Ultracode asks for "the most exhaustive, correct answer" and says "token cost is not a constraint" cited. In this run that meant many agents testing at the same time in real browsers, and the leak grew with the number of agents running at once.
  • No instruction covers disk space. The size guideline counts agents, not bytes. The workflow reference mentions disk once, as a cost of worktree isolation ("~200-500ms setup + disk per agent") cited. Nothing asks the orchestrator to budget or sweep temporary files, and the tokens and dollars in section 7 do not show this cost.
  • Copied tools copy their faults. The orchestrator wrote one capture tool in Phase 0. Agents copied its launch-and-cleanup pattern at least 9 times, each copy with the same fault.
  • A one-off check was not enough. The orchestrator saw the leak once, after WF1, and cleaned up by hand. Without a fix in the tool or a sweep after each workflow, the next six workflows left 133 GB more.

B.6 What would prevent it

  • One shared launcher that shuts down in order: close the browser, kill the process tree and wait for it to exit, then delete the profile with retries and log any failure. Forbid per-agent copies.
  • Far fewer launches: one browser per agent and a new tab per test case. The release-gate verifier's runner did this and left no profiles.
  • One profile folder per workflow, deleted by the orchestrator at the end of each workflow, with the number of gigabytes removed printed in its summary and an alarm above a budget.
  • Smaller profiles, after a test on the Chrome version in use: --disable-gpu-shader-disk-cache, --disable-component-update, --disable-background-networking, --disable-default-apps, --disable-breakpad.
  • Smaller captures: clipped or scaled screenshots for long series, and each agent's screenshots and test builds deleted once its verifier has passed the work.
  • For users: watch the free space during a long ultracode run, and say in the prompt that temporary files must be cleaned up.
