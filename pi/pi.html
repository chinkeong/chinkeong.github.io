A field guide for your first local coding agent, Windows and one graphics card

Run Pi on a model that lives on your own GPU

Pi is a small, fast coding agent. Pointed at a model you serve yourself, it costs nothing per token and never leaves your machine. This page is the setup I run every day on a 24 GB card, a lighter one for 12 and 16 GB cards, and the handful of numbers that decide whether it feels quick or painfully slow.

1,688tokens in Pi's first request with no extensions
23,906the same request with 14 extensions installed
~45 KiBof GPU memory per token of context for the 27B
1-2.5 minto re-read a 60-100k conversation the cache lost

Measured 2026-10-03/04 on an RTX 3090 24 GB with Pi 1.0.0 and llama.cpp build 10502. Token counts come from Pi's real requests, rendered with the model's own chat template; they match what the server reported to the token.

How it fits together

Two programs talk over your loopback network. Pi is the agent: it reads and edits your files, runs commands and keeps the conversation. llama-server (from llama.cpp) holds the model on the GPU and answers Pi's requests on http://localhost:1234, in the same format cloud models use.

Three settings on the server decide almost everything you will notice:

  • -c, the context window: how much conversation the model can see. Llama-server divides it between slots.
  • --parallel, the number of slots. A slot is one conversation the server keeps in GPU memory, with its own cache. --parallel 1 is one slot, --parallel 2 is two, and each slot gets -c divided by --parallel tokens.
  • the model file and its quantisation: smaller files leave more memory for the window.

9B or 27B on a 16 GB card? A standard 3-bit 27B file is 12.3 GB and leaves only about 43,000 tokens, too few once Pi has taken its share. The GSQ-RCO build of Swift-1.5 squeezes the 27B into 10.4 GB at 3.0 bits per weight, which leaves a 75,776-token window for text and about 52,000 tokens of working room in Pi. Take the 27B for harder problems in one conversation at a time; take the 9B for screenshots, two slots and long sessions. Which answers your tasks better was not measured for this page.

A 24 GB card can run the 9B too, with two slots at its full 262,144 tokens each, if you would rather have speed and room than the 27B's strength.

Before you start

Pi is only the agent. The model runs in a separate program, llama-server from llama.cpp, which you install first. You need:

  • Windows 10 or 11 and a graphics card with 12 GB or more. Everything on this page was measured on an NVIDIA card with llama.cpp's CUDA build. Intel Arc and AMD Radeon cards run llama.cpp too, with their own builds (below), but nothing here was tested on them: treat the windows and speeds as a starting point and check them on your card.
  • A recent graphics driver. On NVIDIA, run nvidia-smi in a terminal: the top line shows the driver version, and the CUDA 13 build below needs the 580 series or newer.
  • Disk space for the model: about 6.5 GB for the 9B and 10 to 17 GB for the 27B, vision file included.

Install llama.cpp

llama.cpp has no installer. It is a folder of programs you unzip and run.

  1. Download it. On the releases page, open the newest build, the top entry named like b11382 and marked Pre-release; not every release carries the Windows zips. Which zip depends on your card:
    • NVIDIA: two zips, llama-b…-bin-win-cuda-13.4-x64.zip and the matching cudart-llama-bin-win-cuda-13.4-x64.zip, which holds the CUDA runtime. On a driver older than the 580 series, take the cuda-12.4 pair instead.
    • Intel Arc: llama-b…-bin-win-vulkan-x64.zip.
    • AMD Radeon: llama-b…-bin-win-rocm-…-x64.zip, or the Vulkan zip.
    • The Vulkan zip runs on any card through the normal graphics driver, with no extra runtime to install. On NVIDIA, take the CUDA build: it is what this page was measured with.
  2. Unzip into one folder, for example C:\llama.cpp. On NVIDIA, unzip both zips there: the cudart files must sit next to llama-server.exe.
  3. Check that it sees your card. Open Command Prompt, go to the folder with cd /d C:\llama.cpp and run llama-server.exe --list-devices. Your GPU should be listed with its memory. If only the CPU shows, the build does not match your card, the cudart files are missing (NVIDIA) or the driver is too old for the build.
  4. Updating means downloading a newer release into a fresh folder. Keep the old folder until the new one works.

Coming from Ollama or LM Studio

Both run llama.cpp inside them and choose most settings for you. Here you start llama-server yourself, which is what lets you set the window, the number of slots, the draft head and the cache size the way this page does. Three things to know:

  • Quit them first. A model they keep loaded still holds GPU memory, which comes straight out of your window. LM Studio's server also uses port 1234, the same port as here.
  • LM Studio's downloads are ordinary GGUF files, by default under %USERPROFILE%\.lmstudio\models\<publisher>\<model>. Point -m straight at them instead of downloading again.
  • Ollama stores models under hashed file names, so it is simpler to download the GGUF again from Hugging Face.

Install Pi

  1. Run the installer in PowerShell. It puts the pi command on your PATH.
    powershell -c "irm https://pi.dev/install.ps1 | iex"
  2. Open a new terminal and check it: pi --version should print 1.0 or later.
  3. Keep it current with pi update. Extensions update separately with pi update --extensions.

Run a local model

With llama.cpp installed (see Before you start), two steps get a model answering on your card:

  1. Download the model. You need two files: the GGUF for your card and the mmproj file, which is the vision projector. Either open the model's Hugging Face page, go to Files and click the download arrow next to each, or let curl fetch them. It comes with Windows 10 and 11, so there is nothing to install. Run it in Command Prompt (in PowerShell, type curl.exe); -C - picks up a download that was cut off where it stopped.

For a 24 GB card, the example is Swift-1.5, a 27B Qwen3.8 fine-tune, at IQ4_XS (15.5 GB) with its vision projector, one slot and a 139,264-token window:

24 GB: Swift-1.5 27B, one slot, 139,264 tokens, vision

  --temp 1.0 --top-p 0.95 --top-k 20 --min-p 0.0 ^

  --jinja --load-mode none --api-key dummy ^

16 GB cards: Swift-1.5 27B, GSQ-RCO build

Mean KL divergence from the full-precision Swift-1.5 (lower is closer), on 100 windows of 512 tokens: 0.098 for this 10.4 GB file, against 0.074 for the standard 12.3 GB IQ3_XXS, 0.152 for the standard IQ2_M of about the same size, and 0.018 for the 15.5 GB IQ4_XS. The GSQ figure is on the text its maker tuned with, so it may flatter the file a little. These numbers are cited from ukisai's model cards, not reproduced here.
  • Effort. This command asks for medium reasoning effort. With about 52,000 tokens of working room, one long reply at the highest effort can fill the window by itself; switch to xhigh for a hard problem in a fresh session.
  • Vision is untested. GSQ-RCO ships no vision projector. Swift-1.5's projector from the bartowski repo is built for the same model, and adding it would leave about 56,000 tokens (derived), but this pairing was not run here.
  • The window is derived from the file size and the 3090's measured costs, with the same 0.7 GiB desktop buffer. In Pi, give this setup its own entry with contextWindow and maxTokens set to 75,776.

The speeds the 27B setups measured: about 61-66 tokens a second while generating a long answer at the start of a session, 36 with a 257k-token window 98% full (IQ3_XXS, one slot), and about 25 per conversation when both slots of the two-slot setup work at once on 110k-token histories. The speeds of the 9B and the GSQ-RCO file were not measured for this page.

What each setting means

The commands above share most settings; only the values change. In order of appearance:

SettingWhat it does
Reading the command
^Not a setting. In Command Prompt it continues the command on the next line, so a long command stays readable.
The files
-mThe model file to load: the GGUF you downloaded.
--mmprojThe vision projector, the extra file that lets the model read images. Leave it out for text only and you get back about 0.9 GB.
--image-min-tokens
--image-max-tokens		The fewest and most tokens one image may turn into. More tokens show the model more detail and take more of the window.
--aliasThe model name the server reports. With one model loaded, Pi's model entry does not have to match it.
Memory and the context window
-cThe context window in tokens: how much conversation the model can see. It is the total for all slots, so each slot gets -c divided by --parallel. One slot at 139,264 gives one conversation 139,264 tokens; two slots at 247,808 give each 123,904.
--parallelThe number of slots: how many conversations the server keeps in GPU memory at once, each with its own cache. Always set it. Left on auto, current llama-server opens four slots, and with the draft head on that costs about 2.2 GB more than one slot (derived from llama.cpp's per-slot state).
-ngl 99How many of the model's layers go on the GPU. 99 is more than these models have, so all of them. A number one short leaves the output layer on the CPU and quietly costs about a third of your speed.
-ctk q8_0
-ctv q8_0		Store the context cache (its keys and values) at 8 bits, half the memory of the default 16, for a small, measured quality cost.
--load-mode noneLoad the model without memory-mapping the file. The default maps it, which makes restarts faster but keeps up to the file's size in Windows' file cache in system RAM. How much RAM each mode really holds was not measured here.
Speed: the draft head
--spec-type draft-mtpSpeculative decoding with the draft head built into the model file. The head guesses a few tokens ahead and the model checks them all in one step; correct guesses come almost free, and the model still decides every token. About 80-89% of guesses were accepted in these tests.
--spec-draft-n-maxThe most tokens the head may guess per step. Each one holds more memory in every slot: about 150 MiB on the 27B and 50 MiB on the 9B.
--spec-draft-p-minThe head stops guessing once it is less sure than this (0.75 is 75%) of its next token, so fewer checks are wasted on long shots.
--spec-draft-ngl 99How many layers of the draft model go on the GPU; 99 means all. Used in the 9B commands.
Sampling: how the next token is chosen
--tempRandomness. 1.0 uses the model's own probabilities as they are; lower values make it more predictable. Keep the value each command uses with its model.
--top-p 0.95Choose only among the likeliest tokens that together make up 95% of the probability.
--top-k 20And never from beyond the 20 likeliest.
--min-p 0.0A further cut-off by probability; 0 switches it off.
--presence-penalty
--repeat-penalty		Discourage repeating words already written. 0 and 1.0 mean off; the 9B commands use a mild 1.05 repeat penalty.
Thinking and the chat format
--reasoning-preserveKeep the model's thinking from earlier turns in the history it sees, instead of dropping it. Dropping it would change text the server already holds in its cache, so part of the conversation would be read again; keeping it costs window space.
--chat-template-kwargsPasses a setting into the model's chat template. Here it is reasoning_effort, how long the model thinks before answering: low, medium or xhigh. Higher effort does better on hard problems and uses far more tokens. The backslashes keep the inner quotes intact on the command line.
--jinjaUse the chat template stored in the model file, which lays out Pi's messages and tool calls the way the model was trained to read them.
The connection
--api-key dummyThe key a program must send to use the server. Pi's models.json sends dummy, so they match.
--host 127.0.0.1Accept connections from this PC only. Other machines on your network cannot reach the server.
--port 1234The port Pi connects to. It must match the baseUrl in models.json.

The one mistake that breaks long sessions. Pi decides when to compact from the contextWindow of the model entry you have selected, not from the server. If you run the two-slot server (123,904 per slot) with a 139,264 entry selected, Pi keeps going past the server's real limit and you get overflow errors and retries instead of a clean compaction. Switch entries with Ctrl+P whenever you switch servers.

How big a window

Every token of context costs memory on the card, reserved up front for every slot. For Qwen3.8-27B and its fine-tunes the arithmetic is short:

  • Only 16 of the model's 64 layers keep a cache that grows with context. The other 48 use a fixed-size state.
  • Each of those 16 layers stores 4 heads × 256 values for keys and the same for values. At 8 bits that is 34 KiB a token, plus 4 KiB for the draft head: 38 KiB a token on paper.
  • Measured with the server's working buffers included, it is 44 KiB a token with two slots and 45.9 with one. Plan with the measured figure: about 22,000 tokens per GB of free memory.

When the window is too big, nothing breaks. It just gets slow.

On Windows with an NVIDIA card, memory the card cannot hold spills into system RAM and the server keeps running. A little spill is harmless; past a point the speed falls off a cliff. On the 3090, two slots of the IQ3_XXS file ran at 23 tokens a second each up to 133,120 tokens per slot and dropped to 12 at 135,168 and 5.5 at 139,264. The card's memory reading looked the same on both sides of that cliff; only the speed showed it. So find your largest window by filling it and watching the speed, not by watching memory.

The 9B

Ornith-1.5 9B has the same layout at a smaller size: 8 of its 32 layers keep a cache that grows with context. On paper that is 17 KiB a token at 8 bits plus 4 KiB for the draft head, 21 KiB a token. Adding the 27B's measured buffer overhead on top gives about 27 KiB a token with two slots and 29 with one, or roughly 34,000 tokens per GB of free memory. That errs on the large side, because the 9B's working buffers are smaller than the 27B's.

Your context budget

Before you type a word, Pi sends its system prompt and the definition of every tool it can call. Each extension adds tools, and every tool costs tokens in every request:

Pi setupFirst request, one-line question
Pi alone (pi -ne): read, bash, edit, write1,688
The seven extensions recommended below7,348
Fourteen extensions, including subagents and web access23,906

Then two rules decide how much room is really left:

  • Pi compacts at the window minus 16,384 tokens. With a 139,264 window that is 122,880; with 123,904 it is 107,520.
  • One reply can run to about the window minus 4,096, because Pi only checks between requests. Thinking at the highest effort is hungry: on one demanding coding task, base Qwen3.8-27B wrote 22,700 and 80,200 tokens in two tries, and Swift-1.5 between 52,900 and 67,500.

Rule of thumb. Window, minus 16,384, minus what Pi needs before you type, is your working room. With the recommended extensions and a 139,264 window that is about 115,000 tokens; at 63,488 it would be under 40,000, too small for one long high-effort reply.

To see your own numbers, install pi-context-view and open it in a session: it splits the window into system prompt, tools and free space.

One slot or two

Each slot keeps one conversation's cache. Re-reading a conversation the cache has lost is the slowest thing the server does: on the 3090 about 1 to 2.5 minutes for a 60,000 to 100,000-token history.

Why subagents and one slot do not mix

A subagent is a second conversation. With one slot, its first request throws the main session's cache away, and when it hands back, the main session has to be read again from the start. Llama-server can park an idle slot in system RAM and restore it in a second or so, but its RAM cache is 8 GB by default and on a 32 GB PC it switched itself off at long contexts in these tests, so do not count on it.

With two slots the main session and one subagent each keep their own cache. Coming back is a cache hit: the server read 4 new tokens instead of the whole history in these tests. The main agent waits while the subagent works, so each still runs at full single-conversation speed.

MCP

Pi 1.0 speaks the Model Context Protocol natively, so no extension is needed. Manage servers with /mcp inside Pi or pi mcp add, list, login and logout from a terminal. Servers are defined in mcp.json, globally or per project. Each server's tools can be exposed directly or loaded on demand (the deferred and codemode settings) instead of sitting in every request, which matters on a local model where every token of tool definitions comes out of your window. Details are in the Pi 1.0 release notes.

AGENTS.md

An AGENTS.md in your project folder tells the agent your rules before it does anything. This is mine. Copy it, then cut whatever does not apply: the agent reads every line on every request.

AGENTS.mdthe full file
# AGENTS.md

## Environment Setup
- Scratch/working folder: `%TEMP%\ai_scratch` (PowerShell: `$env:TEMP\ai_scratch`) — derived from the environment, never hardcoded. Create it if it doesn't exist before writing to it.
- If the current date/time isn't already in context, run:
  `powershell -NoProfile -Command "Get-Date -Format 'yyyy-MM-dd HH:mm:ss K (dddd)'"`
- Set UTF-8 before console work that may output non-ASCII text: `chcp 65001` before PowerShell; `-Encoding UTF8` on file reads/writes.

## Non-Interactive Execution
Any command that can prompt for input will hang silently. Always use non-interactive flags:
- `npm install`, `pip install`, package managers → `-y` / `--yes` / `--non-interactive`
- `git commit -m "..."` — never open an editor
- `winget install --accept-package-agreements --accept-source-agreements`

## File Safety
- Read a file before editing it (not needed for new scratch files).
- Use absolute paths always — working directory can shift between tool calls.
- Destructive actions (deletes, force-overwrites, `git push --force`) require an explicit go-ahead in the task before running. Nothing else catches these.

## Calculation Policy
Don't do multi-step arithmetic, unit conversion, or logical derivation purely in reasoning. Write a short script (Python preferred), save it to `%TEMP%\ai_scratch`, run it, read the output back. Fix and re-run on error rather than falling back to mental math.

## Unknowns
If a fact, API, library version, or visual reference isn't reliably known, search the web (or pull a reference image/doc) before answering rather than recalling from memory.

## Task Tracking
Keep a `TODO.md` in the working directory for any multi-step task — check items off as you go. For real coding work: write a small test, implement the minimum to pass it, verify, then move to the next micro-step. Don't write the whole program up front.

## Verification
Before calling a task done, actually check the result — view the screenshot you took, run the test you wrote, open the file you built. One honest check beats several rounds of "does this look right?" self-talk stacked on top of each other. If a step keeps failing, try a genuinely different approach rather than repeating the same fix; after a few honest attempts, stop and report what was tried instead of continuing to loop.

## Screenshots
Default capture: 2560×1440.
```
"C:\Program Files\Google\Chrome\Application\chrome.exe" --headless=new --no-sandbox --disable-gpu --hide-scrollbars --window-size=2560,1440 --virtual-time-budget=5000 --screenshot="%TEMP%\ai_scratch\example.png" "index.html"
```
Use a different resolution if the task names a specific device or viewport. Always view the resulting image before considering the task done.

## HTML/CSS Output Standards

**Layout**
- No fixed `max-width` — layouts must be fluid across viewport widths.
- Font size scales with viewport via `clamp()`, capped at the real values in the reference scale below rather than an arbitrary max — the earlier `2rem` (32px) cap was well under the actual hero heading size (48px), which is why text read small once the font changed:
  `font-size: clamp(1.75rem, 1.5vw + 1.25rem, 3rem);` /* hero heading — caps at 48px, matches the scale below */
- Check the result renders correctly at both ~1280px and 2560px widths against the reference scale below.

**Typography — defaults**
Pick fonts deliberately; don't default to Arial/Times or whatever the last template used.
- General UI / app-like tools: `"Source Sans 3", -apple-system, "Segoe UI", Roboto, Arial, sans-serif`. Source Sans is a free, open-source typeface (on Google Fonts); the rest of the chain is just the fallback if it doesn't load. Note this pulls an external font request, unlike a pure system stack — for offline/air-gapped tools, drop the Source Sans entry and fall back to system-only.
- Content-heavy pages (articles, reports, marketing): pick one of —
  - **One grotesk sans, alone, doing all the work** — e.g. "Public Sans" or "Space Grotesk" for both headings and body, weight and size carrying the hierarchy instead of a second typeface.
  - **Newsreader (serif, headings/body) + IBM Plex Sans (labels/chrome)** — literary without leaning on the cream-background-plus-terracotta look.
- Use a real type scale, not three ad hoc sizes:

  | Use | Size | Weight | Line height |
  |---|---|---|---|
  | Hero / display heading | 48px | 400 | 60px |
  | Section heading (h2) | 32px | 400 | 40px |
  | Body copy (default) | 20px | 400 | 30px |
  | Secondary body / h3 | 16px | 400 / 600 | 24px / 20px |
  | Nav links, primary CTA, inline links | 16px | 600 | 24px |
  | Tertiary links, buttons | 14px | 600 | 17.5px |
  | Captions, footer microcopy | 12px | 400 | 18px |

  Keep display headings at weight 400, not bold — reserve 600 for links, nav, and CTAs only, never headline emphasis (consistent with the "don't bold a word for emphasis" rule below). Keep body line length under ~80 characters; give serif body text extra line-height relative to sans-serif.

**Color**
One brand color plus a tightly disciplined neutral set, not a rainbow of accents:
- `#0a66c2` (primary blue) — reserved for exactly three jobs: the brand mark, the primary CTA, and inline links. Don't dilute it into backgrounds or decorative accents elsewhere.
- `#004182` (blue, dark) — hover/active state for the primary blue only.
- `#000000` (ink) — body and headline text, and every border. Borders are pure black hairlines at 1px, not soft gray — that discipline is what gives chip/card grids a crisp, "tagged" look instead of a soft SaaS-default one.
- `#666666` (ink, muted) — secondary text and metadata only.
- `#ffffff` (canvas) — the page floor.
- `#eae6df` (surface beige) — the one permitted background variation, used to mark a distinct zone (e.g. a sign-in or CTA band). Don't add a second background color on top of this.
- `#b24020` (accent rust) — a single chromatic surprise, used once and sparingly for one promotional or callout element (text/border, never a fill). Extending it into general use dilutes a one-voltage palette into a two-color one.

**Avoid these tells** — the fastest way a page reads as templated:
- Bolding or italicizing a single word in a headline for "emphasis"
- Tracked-out ALL-CAPS eyebrow labels above every heading
- Meta text strung together with middle dots (`A · B · C`)
- Identical rounded cards, same soft grey shadow, on everything regardless of content
- A `→` tacked onto every link or button
- Numbered markers (01 / 02 / 03) on content that isn't actually a sequence

**Motion**: sparing and deliberate — one orchestrated moment, not a fade-and-slide-up on every section and a hover transition on every card.

## Diagrams
Use Mermaid (in HTML output, or as a reasoning aid) when structure, flow, or relationships are clearer visually than in prose.

## Documentation Style
For reference docs, outlines, or specs: use a tree/drill-down structure — trunk (key point) → branches (sub-topics) → leaves (specifics), one idea per indented line. Conversational answers, tradeoff discussions, and narrative explanations stay in prose.
